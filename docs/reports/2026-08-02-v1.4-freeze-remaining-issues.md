# Swob v1.4 内容冻结后的剩余问题

> 盘点时间：2026-08-02 23:25（Asia/Shanghai）<br>
> 对象：`integration/batch9-final-20260802` / `faacffd`<br>
> 结论：代码集成已完成，但当前候选版仍不满足“可以公开发布”的事实条件。

## 一、决策摘要

当前不是“再点一次发布按钮”就能上线。剩余问题分为四类：

1. **运行时健康尚未收口**：真实 Library 可以写，当前活跃会话也能在 60 秒内持续落盘；但全库健康仍是 `identity-conflict / partial`，并存在 stale、unverifiable 和长时间 initializing。
2. **必要交付物缺失**：t187 官方示例包没有 branch/result/deliverable，任务书要求的安装、卸载和恶意包测试无法执行。
3. **最终分支尚未落位**：冻结提交只在集成分支，尚未进入主 checkout；主 checkout 当前有 23 项用户改动，不能直接强行合并。
4. **发布与人工签发尚未执行**：版本仍为 1.3.1；价格签发、Windows 真机、Polar 和发布物料仍有人工门槛。

因此，`faacffd` 应被称为 **v1.4 内容冻结候选**，不能称为“已发布版本”。

## 三、发布阻塞问题

### R1（P0）全库健康合同没有闭环

已证明正常的部分：

- writer 锁处于释放状态，Library 可写；
- 当前活动会话首次 durable backup 在候选版启动后 33 秒出现；
- 三个不同时间点的 backup 都是 source 的精确字节前缀；
- CLI 对事故样本完整 UUID 返回 `matched: true`、`ambiguous: false`；
- 当前活动会话 freshness 为 `fresh`，观测 lag 约 4.5 秒；
- 并发大源不再互相取消，最终正常退出约 1 秒。

仍未解决的部分：

- 真实库约 1,500 个 source 的启动同步逐会话执行全库身份扫描；运行 12 分钟仍停留在 `initializing`；
- 应用退出后的 doctor 仍报告 193 stale、318 unverifiable、13 identity conflicts；
- t189 恢复报告记录的是 3 组获准保留的历史重复身份，而 doctor 输出 13，计数单位或绑定状态没有被统一解释；
- UI 的 `initializing` 同时表达“writer 尚未证明”“后台历史同步未完成”“存在冲突”等不同事实，用户无法判断哪些功能安全可用。

根因不是锁，也不是当前会话监听失效。根因是“前台可用性”和“全库后台重建”被绑成同一个健康终态，同时 Library 身份注册表仍依赖重复的全盘扫描。这是 t194 增量化要处理的核心，而不仅是把 spinner 换个文案。

建议的根治路径：

1. 把健康状态拆成 writer capability、当前活跃源 freshness、后台 backlog、identity exceptions 四个正交维度；
2. writer 证明且活动源 durable 后，在 60 秒内开放无冲突会话的正常使用；历史全库同步转入可观察的后台队列；
3. 用持久化、增量更新的身份注册表取代逐会话重扫整库；
4. 给 3 组已授权保留的历史冲突建立显式 exception 证据，doctor 必须区分“获准只读历史冲突”和“新出现的未知冲突”；
5. 将 318 unverifiable 按缺 source、iCloud placeholder、远端会话、损坏 manifest 等原因拆分，不允许只报一个总数。

验收标准：

- 启动后 60 秒内，writer capability 与活动会话 freshness 都达到可用；
- 可验证且无冲突的会话 stale 为 0；
- doctor 对每个剩余 conflict/unverifiable 给出稳定、可追溯的原因；
- 3 组授权历史冲突与 doctor 计数口径一致；
- 后台同步有进度、剩余数量和失败原因，不再无限显示笼统的 `initializing`。

### R2（P0）t187 官方示例包完全缺失

批次要求验证三个官方示例包的安装与卸载，并实跑路径穿越、携带 JS、超大包等恶意输入。当前没有可用 t187 branch、result.json 或交付物，因此这些验证不是“没来得及跑”，而是“没有对象可跑”。

验收标准：

- 三个示例包有内容寻址或签名证据；
- 安装、启用、停用、卸载全链路通过；
- 路径穿越、符号链接逃逸、可执行脚本、超大包和畸形 manifest 均 fail-closed；
- 打包产物内不包含私有配置、凭据或测试机路径。

### R3（P0）冻结提交尚未进入最终发布分支

`faacffd` 不在当前主 checkout 的祖先链中。主 checkout 同时存在 23 项用户改动，直接 merge/cherry-pick 会把用户未提交工作与发布候选混在一起，也会让冲突归属不可审计。

最短安全路径：

1. 从负责人指定的发布目标创建新的干净 worktree；
2. 在新 worktree 中合入 `faacffd`，逐项处理冲突；
3. 重跑 check、全量测试、packaged CLI 和 real-Library 最小验收；
4. 只在目标分支干净且来源账一致后，宣布“最终分支已落位”。

禁止把“集成分支已经有提交”误报为“主分支已经更新”。

### R4（P0）版本和发布链尚未开始

当前 `package.json` 仍为 1.3.1。本批没有执行：

- v1.4.0 版本升级；
- release commit 与 tag；
- push；
- GitHub Release 和桌面安装包上传；
- update metadata/feed 更新；
- 独立官网仓库部署；
- 已安装客户端自动更新复验。

这是有意保留的安全边界：在 R1-R3 没有解决前，不应该先制造一个公开的 v1.4.0 tag。

## 四、冻结验证缺口

### V1（P1）Insights 只通过自动化测试，真实数据 UI 验收未完成

自动化测试、usage ledger 和 production build 已通过，但真实 Library 在整个观察窗口内没有离开 `initializing`。因此批次要求的以下内容没有形成完整实机证据：

- 全库真实数据零伪 0；
- Token Mix 与 Daily Trend V2 的真实数据交互；
- 筛选、hover、legend、时间范围和空状态；
- 大数据量下的首屏时间、CPU 与内存稳定性。

不能用组件测试代替这部分用户验收。必须在 R1 使应用进入可解释的终态后，用真实数据回放并保留脱敏证据。

### V2（P1）价格 candidate 未签发

t185 的价格候选仍为 `pending-review`，且 `activationAllowed=false`。当前运行时继续使用已批准的 official snapshot，这是正确状态。

剩余动作：

- yyt/负责人逐项核对官方来源、适用维度、时间区间和 unit rule；
- 签发新的 immutable snapshot；
- 重算 content hash；
- 验证历史账本不会被静默重估；
- 只有签发后才允许激活。

### V3（P1）Windows 与外部商业化验收

仍需人工完成：

- Windows CI 截图核对；
- Win11 真机安装、启动、CLI、升级和卸载；
- t177 Polar 状态确认；
- Product Hunt 物料彩排。

这些不是桌面代码单元测试能覆盖的项目。

### V4（P1）官网 14-source 矩阵尚未交付到独立官网

生成器已经验证能输出 14 行并包含 Gemini，但产物只做了临时生成验证，没有写入独立官网仓库，也没有部署。官网在发布前必须从冻结提交重新生成矩阵并校验 schema/hash，不能手工复制旧表格。

## 五、非阻塞但应登记的问题

1. 生产构建仍有三个既有 `::highlight(...)` CSS 优化器警告；当前不影响构建，但应在浏览器兼容性回归中确认。
2. 当前 Library package 分类仍可能把多轮会话放进“单轮会话”容器；本批没有重新处理这一历史分类问题。
3. 授权保留的重复身份仍是只读历史债，未来任何自动整理、移动或合并功能都必须继续 fail-closed。

## 六、推荐执行顺序
